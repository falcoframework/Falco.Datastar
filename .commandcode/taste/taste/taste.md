# Taste
- Expects an adversarial "roast" of their own work before it goes anywhere — unfiltered findings ranked by severity with file, line, and a concrete repro, not encouragement and not style nitpicks. Confidence: 0.9
- Bar for a PR is "absolutely mind-blowingly perfect" delivered in one pass, not incremental approval rounds. Confidence: 0.8
- Any claim about a third-party/upstream API must be checked against the real upstream source (fetch it, read it) rather than recalled or assumed. Confidence: 0.85
- Read-only reconnaissance before conclusions: build it, run the tests, inspect CI workflows, diff against the base branch. Confidence: 0.8
- Docs must be exhaustive: answer and explain everything a reader needs, not a summary. Confidence: 0.85
- Write docs in the user's own voice and the established tone of the source repo, so presentation is cohesive with surrounding material. Confidence: 0.9
- Keep a changelog that also tracks changes in the upstream library being wrapped, version by version. Confidence: 0.8
- Prioritize deterministic simulation testing, mutation testing, and property-based tests; when they are missing, they are high on the list rather than nice-to-haves. Confidence: 0.9
- A broad green signal across the whole matrix (all TFMs, seeds, mutation score, coverage) is the acceptance criterion, not "tests pass". Confidence: 0.85
- CI should exercise what the project actually ships (e.g. solution-level builds) rather than partial paths that hide breakage. Confidence: 0.7
- Frequently contributes to upstream repos maintained by other people; work is judged by whether a maintainer can merge it with zero hesitation. Confidence: 0.85
- When upstream has new releases, fold the relevant changes in rather than letting the binding drift. Confidence: 0.8
- Likes parallel work dispatched for separate review angles (correctness/security vs. docs/parity) to cover ground fast. Confidence: 0.6
- Never edit or generate files via throwaway scripts (Python, shell, codegen); all file changes go through the normal file-edit tools, no matter how awkward the literal content (embedded quotes, escapes, non-ASCII). Throwaway helpers must never be committed. Ad-hoc grep- and bracket-counting scripts are the same failure mode and are just as wasteful — use the real compiler and the SageFs tools for feedback instead. This has now cost real work: two scripted regex passes over a file of ~70 string literals mangled it past the point of repair. Confidence: 0.98
- When a literal string is painful to write by hand, encode it with explicit language escape sequences rather than generating it programmatically. Confidence: 0.85
- Prefers plain `[<Fact>]` xUnit tests that loop over a list of cases internally over `[<Theory>]` + `[<InlineData>]`, so the suite is meaningful under both SageFs live testing and `dotnet test`. Confidence: 0.9
- A `[<Theory>]` failure reported by SageFs `run_tests` ("Parameter count mismatch") is a harness limitation, not a real test failure; confirm with `dotnet test` before acting on it. Confidence: 0.9
- When a check is blocked by something missing on the machine, install it (SDKs, runtimes, browsers) and run the check. A missing local dependency is not a reason to report the gap as unfinished; the user has said plainly to install whatever is needed. Confidence: 0.9
- Never write an assertion from a guess at a format or payload: drive the real code once, read exactly what it produced, then pin those values in the test. Guessed assertions here cost a full rewrite of the file, and some were wrong in ways no amount of staring would have caught. Confidence: 0.85
- Treat a delegated review as a set of claims, not verdicts: reproduce the critical ones before acting on them, because a reported failure can be the reviewer's own in-flight state rather than the real state of the repo. Confidence: 0.85
- Apply the same scrutiny to your own newly written CI, test and infrastructure code as to the code under test; a defect there is worse, because it looks green locally and turns every build red. Confidence: 0.75
- Dogfood SageFs in any repo it can load, at both levels. For the suite: create the project session, hard reset with rebuild when stale or degraded, run the tests there. For an individual change: `check_fsharp_code` to type-check a snippet *before* editing the file, `send_fsharp_code` to inspect real values (an SDK record's fields, a decoded wire format), and `hard_reset_fsi_session` with `rebuild=true` when the session reports stale source. Iterating on a compile error through repeated full builds is far slower and was called out as wasted effort. Confidence: 0.9
- Mutation work has a bar: every mutant must be killable. A survivor is a test gap only if it is not an equivalent mutant, so verify and replace equivalents instead of chasing a test that cannot exist. A "killed" count is meaningless otherwise. Confidence: 0.7
- Report coverage with its blind spots named: F# `inline` members cannot be instrumented, so their zeros inflate the denominator rather than marking untested code. Confidence: 0.7
- On Falco.Datastar the user is not the final owner — Pim is. Do not propose changing how the library is released or deployed to NuGet; that belongs to the maintainer. Their work here is a local copy and local verification. Frame CI steps that touch packaging as local verification, and say so in the comment. Confidence: 0.9
- Before refactoring an artefact that is verified working, commit it or copy it somewhere. A refactor that is abandoned mid-way then has nothing to fall back to; uncommitted work is not recoverable. Confidence: 0.9
- When a new assertion or guard is added, prove it bites: temporarily tighten the threshold to an impossible value, confirm it fails, then restore. A guard that has never been seen to fail is an assumption. Confidence: 0.85
- A property test whose generator almost never produces the interesting input is a test that does not run. Check the generator against the validation rules and measure the mix of outcomes; if one branch is nearly unreachable, build inputs from a curated alphabet and assert a minimum count of each outcome, so a broken generator fails instead of passing quietly. FsCheck's default string generator produces random bytes and a small minority survive strict rules. Confidence: 0.85
- A test that passes `Defaults` and never varies the option pins the dependency, not the library. Vary something observable that the library is responsible for (e.g. set `EventId` and assert the `id:` line reaches the wire) so a real bug in argument pass-through fails it. Confidence: 0.8
- If a refactor demands more escaping gymnastics than the thing it replaced, it is the wrong refactor: add a helper that removes the pain (a `lines` join for source fragments, a tuple-taking constructor) rather than reshaping the data. If several attempts make the file worse rather than better, stop and revert to the working version instead of pressing on. Confidence: 0.8
- A check that only runs when someone remembers to click "Run workflow" rots quietly. Put rot-prone suites (mutation, multi-seed simulation) on a schedule as well as on-demand, so the claim is enforced rather than asserted about one afternoon. Offset scheduled cron off the hour, since every scheduled workflow fires at :00 and queues behind the rest. Confidence: 0.8
- A seed in a test suite is a promise. Implement the PRNG explicitly (SplitMix64 or similar) rather than using `System.Random`, whose algorithm .NET does not promise to keep across versions, and pin the exact values a known seed produces so the algorithm cannot drift silently — a generator that quietly changes is worse than one that is obviously broken, because every recorded replay becomes a lie. Confidence: 0.8
- When adding a testing or tooling pattern that a sibling repository already does well, read that implementation and adapt it rather than inventing from scratch. Asked for "DST like SageFs does it", the transferable patterns came from reading the other F# repos on the machine. Confidence: 0.7
